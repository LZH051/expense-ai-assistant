# 开发问题与设计取舍记录

这份文件用于记录报错、卡点和设计选择。提交时应保留真实的开发过程。

## 已做出的设计选择

### 1. 为什么使用 MySQL

- MySQL 是常见的服务端关系型数据库，适合展示数据库连接与 SQL 能力。
- 使用 InnoDB 后可以真正执行主键、唯一约束和外键约束。
- 数据与 Python 程序分离，更接近正式项目部署方式。

### 2. 为什么金额使用 DECIMAL(10, 2)

金额不能使用 FLOAT。浮点数可能出现精度误差，DECIMAL 可以准确保存两位
小数的金额。

### 3. 为什么给 source_record_id 设置唯一约束

重复运行导入脚本时，`INSERT IGNORE` 会根据该唯一约束跳过已经存在的来源
记录，从而避免重复入库。

### 4. 为什么密码放在 .env

数据库密码和 API Key 都属于敏感信息，不应写进 Python 文件或提交到
GitHub。仓库只提交 `.env.example`。

### 5. 去重逻辑的局限

ETL 使用用户、日期、类别、金额、商户和描述的组合判断重复。如果现实中
同一天确实发生两笔完全相同的消费，这种方法可能误删。正式系统应使用
银行流水号或其他可靠的来源编号。

## 实际遇到的问题与解决过程

### 问题 1：最初使用 SQLite，后来改为 MySQL

- 报错或现象：项目最初使用 SQLite，虽然能够完成三张表和 ETL，但希望使用
  更接近正式项目的服务端数据库。
- 发生步骤：数据库表结构和入库脚本完成后。
- 原因分析：SQLite 适合快速完成本地原型，而 MySQL 更适合练习数据库服务
  连接、账号配置、外键约束和客户端管理。
- 解决方法：将建表语句改成 MySQL 语法；把 `AUTOINCREMENT` 改为
  `AUTO_INCREMENT`，金额改为 `DECIMAL(10, 2)`，日期改为 `DATE`；
  Python 连接从 `sqlite3` 改为 `mysql-connector-python`；SQL 参数占位符
  从 `?` 改为 `%s`。
- 学到的内容：更换数据库不只是修改连接地址，还要检查字段类型、SQL 方言、
  去重语法和日期函数。

### 问题 2：电脑中已经有 MySQL，但程序最初检测不到

- 报错或现象：终端中不能直接执行 `mysql`，也没有发现名为 `MySQL80` 的
  服务，最初以为电脑没有安装 MySQL。
- 发生步骤：准备安装和配置 MySQL 环境时。
- 原因分析：电脑安装的是 Wampserver，自带的 MySQL 没有加入系统 `PATH`，
  服务名称也不是 `MySQL80`，而是 `wampmysqld64`。
- 解决方法：检查 Windows 服务和 Wampserver 安装目录，确认实际使用的是
  MySQL 8.4.7，客户端位于
  `C:\wamp64\bin\mysql\mysql8.4.7\bin`。
- 学到的内容：命令行找不到 `mysql` 不一定表示没有安装，应同时检查服务、
  已安装程序和软件自带的运行环境。

### 问题 3：MySQL 已安装但无法连接

- 报错或现象：`wampmysqld64` 服务最初是 `Stopped`，项目不能连接
  `127.0.0.1:3306`。
- 发生步骤：运行 MySQL 版项目之前。
- 原因分析：数据库文件虽然已经安装，但 MySQL 服务没有启动。
- 解决方法：从 Wampserver 菜单启动 MySQL 服务，随后检查服务状态为
  `Running`，并使用 TCP 测试确认 3306 端口可以连接。
- 学到的内容：“已经安装”“服务正在运行”和“端口能够连接”是三个不同的
  检查层次，不能只看软件图标判断。

### 问题 4：不理解 Python 虚拟环境与 VirtualBox 的区别

- 报错或现象：电脑中已有 Oracle VirtualBox，因此不确定是否还需要创建
  `.venv`。
- 发生步骤：安装 Python 项目依赖时。
- 原因分析：两者都包含“虚拟”一词，但用途不同。VirtualBox 虚拟的是完整
  操作系统，`.venv` 只隔离某个 Python 项目的解释器和第三方包。
- 解决方法：使用 `python -m venv .venv` 创建项目环境，并在 PowerShell
  中激活后安装 `requirements.txt`。
- 学到的内容：虚拟环境可以防止不同 Python 项目之间发生依赖版本冲突，
  不需要为每个项目安装一套虚拟机。

### 问题 5：模拟数据中存在多种异常格式

- 报错或现象：86 条原始记录中包含空类别、`￥188.50`、`1,299.00`、
  不同日期格式、非法日期、非法金额、负数金额和重复记录。
- 发生步骤：ETL 数据清洗。
- 原因分析：真实数据来源通常不统一，如果直接写入数据库，可能导致类型
  错误、统计不准确或重复计算。
- 解决方法：统一去除金额符号和千位逗号；将日期转换为 `YYYY-MM-DD`；
  空类别填为“其他”；删除无法修复的金额、日期和负数记录；按照用户、
  日期、类别、金额、商户和描述组合去重。
- 清洗结果：原始数据 86 条，修复空类别 1 条，删除非法金额 2 条、非法
  日期 1 条、重复记录 1 条，最终保留 82 条。
- 学到的内容：ETL 不只是删除错误数据，还要区分“可以修复的异常”和
  “无法可靠修复的异常”，并保留清洗前后数量作为验收证据。

### 问题 6：重复运行程序可能重复入库

- 报错或现象：主程序会重复生成和导入相同数据，如果没有限制，会导致
  消费金额被重复统计。
- 发生步骤：验证脚本能否重复运行。
- 原因分析：普通 `INSERT` 不会判断来源记录是否已经存在。
- 解决方法：给 `expenses.source_record_id` 添加唯一约束，并使用 MySQL
  的 `INSERT IGNORE`。第一次运行新增 82 条，第二次运行新增 0 条并跳过
  82 条。
- 学到的内容：可重复安全执行的程序称为具有幂等性，唯一约束应由数据库
  兜底，不能只依赖 Python 查询后再决定是否插入。

### 问题 7：ChatGPT Plus 不能直接作为项目 API 使用

- 报错或现象：已有 ChatGPT Plus 会员，但无法直接得到可供 Python 调用的
  免费 OpenAI API 次数。
- 发生步骤：选择大模型接口时。
- 原因分析：ChatGPT 订阅和 OpenAI API 是两个独立计费系统，Plus 会员不
  包含 API 调用余额。
- 解决方法：改用已有余额的火山方舟豆包 API。火山方舟兼容 OpenAI Python
  SDK，因此项目只需在 `.env` 中更换 `AI_API_KEY`、`AI_BASE_URL` 和
  `AI_MODEL`，不需要重写完整调用流程。
- 学到的内容：使用“大模型产品”和调用“大模型 API”不是同一件事；接入前
  要确认鉴权方式、计费方式、Base URL 和模型 ID。

### 问题 8：如何确认 AI 结果确实与消费数据相关

- 报错或现象：仅看到“API 调用成功”不能证明结果满足作业要求。
- 发生步骤：生成 `output/ai_analysis.txt` 后。
- 原因分析：模型可能返回泛泛的建议，也可能引用不存在的数据。
- 解决方法：将 AI 输出与 `statistics.json` 逐项对比。结果正确识别了总
  消费约 2.08 万元、住房支出 7221.98 元、3 月消费最高，以及 2 月购物
  超预算 574.38 元，并给出三条具体建议。
- 学到的内容：大模型返回成功只是技术验收，内容还需要与结构化统计数据
  进行事实核对，避免模型生成错误结论。

## 尚未解决或后续可改进

- 当前本地开发环境使用高权限数据库账号，正式部署时应创建只拥有本项目
  数据库权限的独立用户，并设置强密码。
- 目前去重规则可能误删同一天发生的两笔完全相同的真实消费，正式系统应
  使用银行流水号等可靠的业务唯一编号。
- 当前 AI 分析一次处理完整统计 JSON；后续可增加结果格式校验、失败重试、
  调用用量记录和预算预警规则。
